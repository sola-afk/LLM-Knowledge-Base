## Open Questions for the Designer

1. **Population retrieval is lossy.** `fireflies_get_transcripts` caps at 50 and truncates the oldest day silently. The run spec should mandate day-by-day pagination for any multi-day range.
2. **The Step 1 domain filter is wrong.** `yonder.app` / `goyonder.io` are Kota-side. As written the filter treats Kota staff as customers.
3. **HF numbering conflicts between the two source documents.** `req-detection-criteria.md` has HF-07 = circumvention language and HF-08 = recording consent. `spec-eval-daily-run.md` has HF-08 = absolute-certainty claims, SF-10 = circumvention, and HF-06/HF-07 = recording consent (excluded). The run spec has been treated as operative here. **The two documents must be reconciled** — findings have already been mislabelled against the criteria doc's numbering (see the correction note below).
4. **Volume vs method.** 51 customer-facing calls a week cannot be reviewed at transcript level in a single pass at this cost. Either the run needs to be daily (13/day was tractable in June), or the spec needs an explicit, documented sampling rule — a risk-weighted sample stated as a sample — rather than a full-population claim that quietly becomes a summary skim.
